# Digests

## Why

Too much AI news. Every issue of every AI newsletter lands in the feed as its own
Highlights, and the same launch shows up five times in five wordings. What is wanted
instead is a few answers on a calendar: "what moved for local models that fit 12GB
VRAM", "the 5 best new tools since the last issue", "what were the hot topics".

A Pipeline cannot do this. It fires `on_new_document`, sees one Document, and dedups
only against its own feed (`ListRecentTopicHighlightsByFeed`). A Digest is the missing
cross-Document, calendar-driven stage.

## Shape

Two stages. Stage 1 exists.

1. **Per issue (existing Pipelines).** `llm_ai_newsletter` and friends turn each
   Document into Highlights. Unchanged, except those Highlights can be held out of
   the feed (see "Hold").
2. **Per period (new).** A `run_digest` Job collects the Highlights created since the
   Digest's last issue, from the selected Feeds, and asks each question once. Output
   is one `DigestIssue`.

**A Digest reads Highlights, never Documents.** No re-fetch, no re-read of a whole
newsletter, and the input is small enough for one call per question. Consequence: a
Feed with no Pipeline producing Highlights contributes nothing — the editor says so
next to that Feed instead of failing silently.

## Vocabulary (add to both CLAUDE.md lists)

`Digest` (the config) · `DigestIssue` (one run's output) · `DigestQuestion` (one
editable prompt inside a Digest) · `DigestTopic` (one grouped answer item).
Tables `digests`, `digest_issues`. Questions and topics are JSON inside their parent
row: a question is edited only with its Digest, an issue is immutable once written.

## Data

```sql
digests (
  id, name, enabled,
  period          TEXT,     -- daily | weekly (no monthly: decided 2026-10-01)
  weekdays        TEXT,     -- JSON [2,5]; weekly only. Tue+Fri = one weekly Digest, two days
  hour            INTEGER,  -- local hour the run is due
  source_feed_ids TEXT,     -- JSON; [] = every Feed
  questions       TEXT,     -- JSON [{id,title,prompt,top_n,enabled}]
  provider, model,          -- Router id + model, same picker as a PipelineStep
  hold_highlights INTEGER,
  next_run_at, last_run_at,
  created_at, updated_at, rev, deleted_at
)

digest_issues (
  id, digest_id,
  window_start, window_end,
  status          TEXT,     -- running | done | empty | failed
  topics          TEXT,     -- JSON, see below
  metadata        TEXT,     -- provenance per question: model, provider, tokens, prompt_sha, truncated
  created_at, updated_at, rev, deleted_at
)
```

Both additive → `additiveMigrations`.

Topic shape:

```json
{"question_id":"…","question_title":"Cool tools","rank":1,
 "title":"…","why":"…",
 "refs":[{"highlight_id":"…","bullet":2}, {"highlight_id":"…","bullet":-1}]}
```

`bullet` is the line index inside the Highlight body, `-1` = the whole Highlight.
That is what "linking each to the bulletpoint" needs: a summary Highlight is seven
bullets about seven things, so a topic must be able to point at one of them.

## The window is "since the last issue", not the period

`window_start = last_run_at` (first run: one period back). A skipped or failed run
therefore loses nothing — the next one covers the gap. This is also what makes "tools
that came out since the last summary" true by construction.

## The LLM call

One call per enabled question. Input: the candidate list, the question's prompt, and
the previous issue's topic titles for that question as "already covered".

- **Candidates are numbered, never addressed by UUID.** Each line is
  `[17.2] <feed title> · <highlight title> — <bullet text>`. The model returns
  `"refs":["17.2","31"]`; the server maps them back. A 4B local model mangles UUIDs.
- **The model writes only `title` and `why`.** Every bullet shown under a topic is the
  stored Highlight text, resolved from a ref. Refs that do not resolve are dropped; a
  topic left with no refs is dropped. This is the `partition` lesson from
  `docs/decisions.md` applied here: a pass that never saw the Document must not be
  allowed to write its facts.
- **Grouping and semantic dedup happen in this same call.** No embeddings in the
  stack, and at this size none are needed: the prompt contract is "items about the
  same thing are ONE topic; list every ref".
- **Budget.** A week of ten newsletters is ~80 candidate lines, ~5k tokens.
  Over budget (`EstimateTokens` against the route's `ctx_tokens`): keep newest
  first, clamp, record `truncated` in metadata and show it on the issue. Never
  silent.
- **Metering.** `llmCall` is tied to a `PipelineRun`. Extract the route + ledger +
  provenance part into a helper both it and the digest use; do not write a second
  path to the Router. `llm_usages` row with `job_id` set, `pipeline_run_id` nil
  (precedent: `/llm/ask`).
- **Rule 5.** A Digest whose scope includes a Feed with scraper auth must route to a
  local provider. Enforce at save AND at run (a Feed can gain auth later); fail loud.

## Scheduling

`worker.scheduleDigests` on the existing 60s tick, same pattern as
`schedulePollFeeds`: due + enabled → insert `run_digest`, bump `next_run_at` first so
a tick cannot double-enqueue. `next_run_at` is computed in the server's local zone.
The Job reports through `progress` (`phase: llm`, question n/m) for free.

`POST /api/v1/digests/{id}/run` inserts the same Job — "Run now" in the UI, and how
the e2e drives it.

## Hold

`hold_highlights` on a Digest: Highlights from its scoped Feeds are archived as the
pipeline run completes, so they never sit in the feed between issues. One site, at
run completion in `handleRunPipelineStep` — not inside each step's insert.

Open: they are briefly visible to a device that syncs mid-run. If that shows in
practice, move the stamp into `InsertTx`.

## API

`GET/POST /api/v1/digests`, `GET/PATCH/DELETE /api/v1/digests/{id}`,
`POST /api/v1/digests/{id}/run`, `GET /api/v1/digests/{id}/issues`,
`GET /api/v1/digest-issues/{id}` (refs resolved: bullet text, Document id + title,
Feed title). `GET /api/v1/digest-question-defaults` serves the starter questions the
way `/pipeline-steps` serves the catalog, so the app hardcodes no prompt.

Starter questions: *Local intelligence for 12GB VRAM* · *Cool tools (top 5)* ·
*Hot topics*.

## App

- `/digests` — list: name, period, enable switch, last issue date, next run. Add.
- Editor — name · period + weekdays + hour · newsletter multi-select (from
  Subscriptions, with a "no Highlights yet" marker) · questions: add, remove,
  reorder, enable, title, prompt textarea, top N · provider/model picker (lift the one
  in `pipelines.tsx`, do not copy it) · hold switch · Run now.
- `/digest/[id]` — an issue: question → ranked topics → the bullets, each one opening
  its source Highlight/Document. Issue picker for older ones.
- Issues sync one-way into the local SQLite (machine data), so they read offline.
  Editing a Digest is online-only, like Pipelines.
- Add `/digests` and a seeded `/digest/<id>` to `e2e/smoke.js` `PAGES`.

## Vault

- Each issue → `digests/<digest-slug>/<date>.md`: questions as headings, topics as
  sub-headings, bullets with wikilinks to the Document notes. Written through
  `writeNote`, so an idle sweep stays quiet.
- **Raise before implementing:** Digest *config* has no markdown path, and neither do
  Pipelines today (`export.go` never mentions them). That is an existing gap against
  rule 1, not one this plan should widen quietly. Decided 2026-10-01: export both as
  front-matter notes, as its OWN plan after this one. Not in scope here.

## Self-test (decided before starting)

Seed through the API / harness: three Feeds, A and B covering the same launch in
different wording, C carrying an unrelated item. A Digest scoped to A + B with one
question. LLM = the stub box the harness already runs for config-test.toml.

`just e2e-int`, driven through the UI:
1. Create the Digest in the editor, pick A and B, edit the question's prompt, save,
   reload → the edit is still there.
2. Run now → the issue page shows ONE topic carrying TWO bullets, one per newsletter.
   Nothing from C anywhere on the page.
3. Click the second bullet → lands on B's Document.
4. Disable the Digest in the list → the switch survives a reload.

Go tests: `next_run_at` for daily and weekly incl. Tue+Fri across a week boundary · disabled never
enqueues · the window starts at `last_run_at` · unresolvable refs and ref-less topics
dropped · over-budget clamps and marks `truncated` · auth-scoped Feed + cloud provider
refused.

Not verifiable headless: nothing here is native-only, but the APK must be rebuilt for
the phone to see the screen.
